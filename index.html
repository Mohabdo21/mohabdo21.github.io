About

I have spent 13 years in IT. The first ten were at All In One in Khartoum, in the hardware and support roles listed below: component-level repair, network configuration, hardened system imaging across multi-user environments, and ownership of backup schedules and data recovery. I also ran a translation and documentation desk there, producing certified English-Arabic translations and bilingual documents with right-to-left layout. It taught me how systems fail, and how to stay calm while they are failing.

In 2023 I made a deliberate move into software engineering and completed the ALX back-end programme. Since then my work has been contract and volunteer engineering across four teams, and every engagement has shipped to real users rather than stopping at a demo. The pattern is consistent: I build the backend, I own the delivery pipeline, and I leave the deployment documented and observable.

What I think I am actually good at is the seam between writing services and running them. I have written the Go service that ingests over two million telemetry messages a day, and I have been the person paged at 2am when it stopped. That is why my pipeline work is opinionated, why I default to least privilege and to signed artefacts, and why I write the runbook before I need it.

ITSQ

Enterprise IoT Monitoring Platform

Client contract

Dates
May 2025 - May 2026
Location
Qatar, remote contract

Co-developed. Owned the infrastructure and the delivery pipeline.

2M+ telemetry records processed daily

A multi-tenant platform ingesting and visualising real-time LoRaWAN telemetry from physical devices, processing over 2 million records daily.

  • Tenant isolation with PostgreSQL Row-Level Security across more than 30 tables, combined with role-based access control. The isolation is enforced in the database rather than filtered in the application, so a query written in the wrong place cannot leak another tenant's data.
  • A sandboxed JavaScript decoder engine that runs untrusted device payloads inside V8 sandboxes, with multi-layer security analysis. Security as a design decision, not a bolt-on.
  • Go microservices for MQTT ingestion, payload decoding and time-series persistence, wired together with RabbitMQ and gRPC.
  • A FastAPI backend streaming live updates to the dashboard over Server-Sent Events, with Redis caching.
  • A React single-page application built from scratch: 100+ components, TypeScript in strict mode, RTK Query, real-time SSE dashboards, tested with React Testing Library and MSW.
  • Delivery on Docker Compose across a VPS, with 14 GitHub Actions workflows covering change detection, build, test, Trivy scanning, cosign image signing and automated production deploys.
  • Zero-downtime deploys: signed-image verification, dependency-ordered rolling updates, health checks and automated database migrations.
  • Prometheus, Grafana and Loki with custom dashboards, alerting and automated config sync. Incidents triaged from alert to root cause.
  • The edge and the data path hardened: Nginx with TLS, security headers and rate limiting; MQTT broker with TLS and ACLs; scheduled pgbackrest backups and automated SSL renewal.
Architecture

Read as: devices publish over MQTT with TLS into a broker restricted by ACLs. RabbitMQ fans out to Go services for ingestion, payload decoding and time-series writes. Untrusted device payloads are executed inside a V8 sandbox rather than trusted. TimescaleDB enforces tenant isolation in the database with row-level security across more than 30 tables. A FastAPI backend with Redis caching streams server-sent events to a React dashboard, while Prometheus, Grafana and Loki observe the whole path. The runtime was Docker Compose on a VPS; a Kubernetes deployment with kustomize, HPA, NetworkPolicies and RBAC was architected and configured alongside it, but it was not the system serving production traffic.

Operations and reliability

Judgement, not a checklist. The production evidence for all of it is in the projects above, and the hardware decade below is where the instinct came from.

Ownership ends at the last log line
A service is not finished when it merges. It is finished when someone else can run it at 2am without me, and when whatever broke it last time cannot break it again.
Fail closed, on purpose
Deny by default. Migrations reversible. Deploys additive. Pick the failure mode that is safe rather than the one that is convenient.
Automate whatever paged me twice
A recurring fault becomes a check in the pipeline. If it can be detected, it should fail the build rather than the on-call.
The runbook is part of the change
Written before the deploy, not after the incident. Ten years of hardware triage is where that habit comes from.
